# ADR-0006: Event-log hash chain and snapshot cadence

- **Status:** Proposed (the maintainer's merge of the pull request records acceptance; see the [index](README.md))
- **Date:** 2026-11-04
- **Deciders:** bioedca (maintainer). Drafted by Claude Code (cloud), bootstrap task 16 ([PRD 42](../prd/42-bootstrap-backlog.md) row 16).

## Context

Every change in Tlilli is an event, and the UI and the MCP server emit events through the same core API (`INV-02`). The concept chose "an append-only event log with materialized snapshots" so that "runs, diffs and rollback cost nothing extra", and it made the span the unit of address: a sentence with a stable ID preserved across edits by diff anchoring, on which comments, requests, claim links and provenance marks hang (`INV-05`, `INV-06`, `INV-10`). [PRD 21 §3](../prd/21-architecture-and-tech-stack.md#3-technology-decisions) and [§4](../prd/21-architecture-and-tech-stack.md#4-core-model-boundaries) lock the shape: ULID block IDs; span IDs derived by segmentation and stabilized by diff anchoring with `similar`; one event enum where every mutation carries `actor` (`Author`, `Agent{run_id, identity}`, `System`), `at`, `parent_hash` and `payload`, validated against the pen rule (`INV-01`); CRDTs rejected because there is no multi-writer need.

The requirements set the bars. Replay of the log from genesis reproduces the current state byte-for-byte, and the hash chain detects a tampered or truncated log (`FR-01-030`). Snapshots are taken on Send, on import, every 50 events or 10 minutes while editing, and on demand with a label; they are immutable, deduplicated by content-addressed blocks, and restoring one creates a new event (`FR-01-031`); runs take `before` and `after` snapshots (`FR-02-002`); a snapshot is created in ≤ 100 ms and a diff renders in ≤ 1 s (`NFR-PERF-004`). A crash or power loss loses at most the last uncommitted transaction, ≤ 1 s of typing (`NFR-REL-001` as amended by D-066 in pull request 52, which prescribes `synchronous=FULL` for the workspace database); startup verifies the chain and rebuilds snapshots that disagree with the log (`NFR-REL-002`); autosave is continuous (`NFR-REL-007`). Typing latency to a committed event is ≤ 16 ms at p95 and the reference manuscript opens in ≤ 2 s cold (`NFR-PERF-002`, `NFR-PERF-001`). Span IDs survive author edits: similarity ≥ 0.6 by position-aware normalized token overlap keeps the ID, new sentences mint IDs, deleted ones leave tombstones pointing at the nearest survivor; ≥ 99% of untouched sentences and 100% of locked spans keep their IDs on the revision corpus (`FR-01-012`, [PRD 01 §6](../prd/01-vision-and-scope.md#6-success-metrics), R-01). Undo and redo are event-based and cross sessions (`FR-01-020`); rolling back a run appends new events and lists conflicts (`FR-02-045`). The PRD names no hash algorithm, no chain scope and no compaction rule; this ADR fills those gaps.

## Decision

**Events.** One row per event in `events` (ADR-0004). Each event belongs to one chain: `chain_id` is the manuscript's ULID for manuscript events and `workspace` for workspace-scoped events, and `seq` counts from 1 without gaps within that chain; ordering is by (`chain_id`, `seq`), never by clock. Each event also carries `group_seq` (the `seq` of the first event of its commit group, below), `actor`, `at` (UTC RFC 3339, informational), `parent_hash`, `hash`, `payload_version` and `payload`. Events are immutable once committed; migrations never rewrite them (ADR-0004, migration rule 4).

**Hash chain.** `hash = SHA-256(canonical_json({chain_id, seq, group_seq, actor, at, parent_hash, payload_version, payload}))`, where `canonical_json` is the deterministic serialization the canonical export uses (stable key order, LF, `FR-01-043`). `parent_hash` is the `hash` of the event with the previous `seq` in the same chain, and `seq` 1 has an all-zero parent. A chain alone cannot show that its tail, or a whole manuscript chain, was removed, so every chain has independently stored expected heads: the `chain_heads` row (`chain_id`, `head_seq`, `head_hash`), moved to the last event of each commit group in the transaction that appends the group (ADR-0004); the head every snapshot repeats (`head_seq`, `head_hash`); and, in the workspace chain, a `System` event recording a manuscript chain's head whenever that manuscript is created, archived or permanently deleted and whenever a snapshot of it is taken. Permanent deletion (`FR-01-002`) is the one operation that removes events: the manuscript's events, its `chain_heads` row, its snapshots and its materialized rows go in one transaction with that workspace event, which records the chain's final head, so verification reads the absence as a deletion, not a loss. The `chain_heads` row is removed rather than kept as a tombstone, because the workspace event is already a durable record of the deletion and is itself covered by the workspace chain's exact-head check. SHA-256 is the option taken because the project already uses it for release checksums (`NFR-SEC-007`), a pure-Rust implementation exists, and one hash of a small payload per event is far inside the 16 ms budget. Verification is a single pass over each chain recomputing hashes and parents, followed by a check of every expected head: the recomputed tip must equal `chain_heads` exactly, and each historical head (each snapshot's, and each one the workspace chain records) must be a prefix of the chain, that is, the event at its `head_seq` must exist and carry its `head_hash`. A chain whose permanent deletion the workspace chain records is the exception: its earlier heads are not checked against it, and the check is that nothing of it is left (no event, no `chain_heads` row, no snapshot). It reports, per `FR-01-030`: *tampered* when a stored hash or parent differs from the recomputed one (with the first `seq` that disagrees), when the event at a recorded `head_seq` carries a different hash, when a chain that has events has no `chain_heads` row, when anything of a deleted chain is left, or when an event's `group_seq` is neither its own `seq` nor its predecessor's `group_seq`; *truncated* when the chain is consistent but ends before a recorded `head_seq` (with the recorded and the found `seq`); *missing chain* when heads are recorded for a manuscript that has no events and no recorded permanent deletion; *gap* when `seq` within a chain is not contiguous from 1. A finding is shown to the author with the last consistent `seq` and the backups available; appending to that chain is refused until the author restores a backup or accepts the found state, and that resolution is itself a `System` event. Changing the algorithm later means a new chain genesis and is a breaking storage change that needs an ADR.

**Self-describing payloads.** An event records outcomes, not only inputs: a text-edit event carries the edited text and the resulting span table of the touched paragraph (span IDs in order, tombstones with their successors, provenance marks), computed once at commit time by segmentation and diff anchoring. Replay applies recorded results and never re-runs the segmenter, so `replay(log) == state` holds byte-for-byte even after segmentation rules, abbreviation lists or the anchoring threshold change between versions (`FR-01-030`, `PR-TST-005`). Minted ULIDs are in the payload for the same reason. `payload_version` lets the decoder read every payload format ever released (`PR-MNT-005`).

**Commit groups.** `FR-01-020` is the binding rule: every ProseMirror transaction maps to one or more core events. The Editor row of [PRD 21 §3](../prd/21-architecture-and-tech-stack.md#3-technology-decisions) says "transactions map 1:1 to core events" in its rationale column; the 1:1 holds between transactions and commit groups, and that wording is listed for the PRD amendment ([PRD changes pending](README.md#prd-changes-pending)). A commit group is what one core call appends to one chain: one ProseMirror transaction, one MCP write-tool call or one `System` action. Its events are consecutive and share one `group_seq`, the `seq` of the first; they are appended in one SQLite transaction that also moves `chain_heads` to the group's last event. A call that writes two chains (a manuscript event and the workspace event that records it) writes one group in each, in the same SQLite transaction. The group is the one boundary for everything: a crash leaves a group wholly committed or absent; the core confirms a group to its caller only after the commit has returned (`FR-01-030`), and the view re-renders once per confirmed group from the core's response (`INV-02`); an undo step reverts one or more whole groups, never part of one, and undo and redo each append a new group, so the boundary is in the log and survives a restart (`FR-01-020`).

**Durability and the crash budget.** `NFR-REL-001`, as amended by D-066 (pull request 52), bounds the loss on a crash or power loss to the last uncommitted transaction and prescribes `synchronous=FULL` for the workspace database, because in WAL mode `synchronous=NORMAL` can drop committed transactions whose WAL frames were not yet synced when power is lost. `workspace.sqlite` therefore runs with `PRAGMA synchronous=FULL`: every commit is fsynced to the WAL before it returns, a UI-confirmed event is never lost, and an application crash loses nothing committed either. Checkpointing is then a performance matter, not a durability one (below). The per-commit fsync sits on the typing path and is measured by the `NFR-PERF-002` bench; the kill-9 harness and the recovery property test verify both crash cases. ADR-0004 states the same setting for the workspace database.

**Failed commit.** The core computes a group's result on its in-memory state before the commit, and that state stays provisional until the commit returns. If a statement of the SQLite transaction or the `COMMIT` itself fails (for example `SQLITE_FULL`, `SQLITE_IOERR`, or `SQLITE_BUSY` once the busy timeout has passed), the core rolls the transaction back unless SQLite already has (`sqlite3_get_autocommit` tells which), discards the chain's provisional state and reloads it from `chain_heads` and the chain's materialized rows in a new read transaction, so the database and not memory decides what the chain holds. The caller gets an error, not a confirmation: the view keeps its last confirmed state, as it does when a core response is dropped (`FR-01-020`), and the status bar says that the edit was not saved; an MCP write tool returns an error. Appends to that chain are refused until the reload has succeeded. While the reload or the next commit keeps failing (a full disk, a read-only folder, a failing device), the manuscript stays read-only, with the cause and a Retry action in the status bar. The `commit_failure` fault-injection test in `tlilli-core::storage` makes each step fail in turn for every event type (an `events` insert, the `chain_heads` update, and the `COMMIT`, the last through SQLite's commit hook, which turns a commit into a rollback) and asserts that nothing was confirmed, that the reloaded state equals `replay(log)`, and that the next append extends the committed head.

**Checkpoints.** The thresholds below say when a checkpoint is attempted, not how old or large the WAL can get, because a checkpoint cannot move frames past an active reader's end mark ([SQLite: write-ahead logging](https://www.sqlite.org/wal.html), checkpoint starvation). SQLite's automatic checkpoint runs `PASSIVE` on the committing connection after a commit once the WAL holds 1,000 frames (`sqlite3_wal_autocheckpoint`). It is a setting of each connection, and every new connection starts with it on, so every connection `tlilli-core` opens, in every process and whatever its role (writer, reader or the checkpoint task below), runs `PRAGMA wal_autocheckpoint=0` as it opens; no checkpoint then runs on the typing path. Instead a background task in `tlilli-core::storage`, on a connection of its own, calls [`sqlite3_wal_checkpoint_v2`](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html) in `PASSIVE` mode every 1 s while the WAL holds frames not yet checkpointed, and at once when it exceeds 1,000 frames (about 4 MB at the default page size). `PASSIVE` never waits and never calls the busy handler, so it cannot delay a commit, but it leaves behind the frames that an open reader still needs. The task compares the frame counts the call returns; when frames have been left behind for 30 s, or the WAL exceeds 10,000 frames (about 40 MB), it escalates once to `TRUNCATE`, with its busy handler bounded at 100 ms and only after 1 s without a commit, because `FULL`, `RESTART` and `TRUNCATE` wait for readers and block new writers while they are pending. When the escalation returns `SQLITE_BUSY`, SQLite has already checkpointed what it could as `PASSIVE` would; the task returns to the `PASSIVE` schedule and escalates again at the earliest 30 s later. Every process that opens the workspace through `tlilli-core` (the app, the standalone `tlilli-mcp`, the `tlilli` CLI) runs the same task; a checkpoint that finds another one running gets `SQLITE_BUSY` at once and waits for the next tick. Reader lifetime is a core rule: a read transaction lives only for the call that opens it and is never held across a UI event, a tool call's wait or an await on I/O, and a read that needs a consistent view copies what it needs and closes the transaction before rendering or exporting. Readers outside Tlilli (an SQLite browser left open, a backup tool) can still pin the WAL. The fallback is that the WAL grows while every committed event stays durable; if it stays above 10,000 frames for 5 minutes, the status bar says that another program is holding the workspace database open. The PRD fixes none of these numbers; they are the option taken, and the `NFR-PERF-002` bench may tune them. A storage test holds a read transaction open from a second process while the writer commits past 10,000 frames, and asserts that commit latency stays within the `NFR-PERF-002` budget, that `PASSIVE` reports frames left behind, that the escalation returns `SQLITE_BUSY` within its bound, that the core raises the held-open warning, and that once the reader closes the next checkpoint moves every frame and the escalation empties the WAL.

**Snapshots.** A snapshot belongs to one chain and holds the complete state that chain's events build, in the layout ADR-0004 defines ("Snapshot contents"): a text part with the sections in order and each block, under its section, with its spans and provenance marks; and a record part with every other table the chain builds (annotations, span tombstones, runs and their calls, ledger rows, the style sheet). Tombstones are records, so the ones whose block was deleted stay in the snapshot. Everything is stored once in content-addressed `snapshot_blocks` (`FR-01-031`), and the metadata is `kind`, `label`, `head_seq`, `head_hash` and a `root_hash` over the chain, the head and the ordered tree, so section identity and order are covered. A workspace snapshot has no text part. Cadence: on Send (`before`), on run close (`after`), on import, on demand with a label, and automatically every 50 events or 10 minutes while editing, whichever comes first, with the timer reset by every snapshot; the workspace chain takes one every 50 of its events. Snapshots are immutable: restore appends events that bring the text part back and keeps IDs (`FR-01-031`), and recovery never rewrites a snapshot (ADR-0004). At startup the core selects, independently for each manuscript chain and for the workspace chain, the newest snapshot that is a valid replay base (its `head_seq` and `head_hash` match the verified chain, every block it references hashes to its key, and its tree hashes to its `root_hash`), replays that chain's events after the snapshot's `head_seq`, and compares the result with the chain's materialized tables, which are rebuilt if they disagree (`NFR-REL-002`). A snapshot that fails those checks is reported, left unchanged and skipped in favour of the next older one, down to genesis; after any rebuild a new snapshot of kind `recovery` is written at the chain's current head. Because automatic snapshots come every 50 events, each chain normally replays a short tail, which keeps cold open within `NFR-PERF-001`; chain verification still covers every event.

**No compaction.** The log is append-only and never truncated or rewritten; the only removal is the permanent deletion of a whole manuscript chain described above, which the workspace chain records. Compaction would defeat the truncation detection `FR-01-030` requires and the replay-from-genesis property. Snapshots are not deleted in v1 either, except with their manuscript on permanent deletion, which also removes the blocks no remaining snapshot references and keeps those another snapshot shares (ADR-0004); deduplication keeps automatic snapshots cheap because only changed blocks are stored. If measured growth on the reference workspace threatens `NFR-PERF-001` or `NFR-PERF-009`, the first lever is a verified checkpoint hash that lets startup verify only the tail, recorded as a follow-up decision rather than assumed now.

**Span-ID stability.** At commit time the touched paragraph is re-segmented (`FR-01-011`) and the old and new span lists are aligned with `similar` using position-aware normalized token overlap: similarity ≥ 0.6 keeps the ID, lower mints a ULID, and unmatched old spans become tombstones pointing at the nearest surviving span (`FR-01-012`). Nearest is in document order across the manuscript, looking back first: the closest surviving span before the deleted one, else the closest after it, so the tombstones of a deleted paragraph point at the last surviving span before it. Only when no span of the manuscript survives does a tombstone point at the block that held the span or, if that block is gone too, at its section; when neither survives, the tombstone is an orphan with no successor. Successors are chosen at commit time and recorded in the payload with the rest of the span table. When one old span matches two new ones (a split), the earlier new span keeps the ID, mirroring the block rule in `FR-01-010`; when two old spans match one new one (a merge), the first keeps its ID and the second is tombstoned. Locked spans ("do not touch", `FR-01-021`, `FR-04-003`) are read-only to agents, not to the author, and they keep their ID through any author edit confined to them, whatever the similarity: the lock and every anchor hang on that ID, and [PRD 01 §6](../prd/01-vision-and-scope.md#6-success-metrics) targets 100% survival for locked spans, which the similarity rule of `FR-01-012` (silent on locked spans) cannot guarantee. Splitting a locked span keeps the ID on the first part; in a merge the locked span's ID is kept (the first, if both are locked); deleting a locked span outright tombstones it like any span. Both metrics are measured at G1. Anchors (comments, requests, claim links, provenance marks) reference span IDs and follow them; tombstones resolve to a neighbour for display by following successors. An anchor whose resolution ends at an orphan, or at a block or section removed since, is shown as orphaned in the pane that lists it until the author re-anchors it with the manual re-anchor control (R-01) or removes it. Blocks keep their ULIDs on split (first half), merge (first) and move (`FR-01-010`).

## Consequences

### Positive

- Tampering and truncation are detectable, and replay equality is a tested property ([PRD 34 §3](../prd/34-testing.md#3-what-to-test-by-component), Event log).
- Runs, diffs, rollback, cross-session undo and provenance come from the same log with no extra bookkeeping (`INV-05`, `INV-06`).
- Replay does not depend on the segmenter's version, so improving segmentation never moves old anchors (R-01).

### Negative

- Payloads carry span tables, so the log is larger than an input-only log, and the database grows without bound.
- Hashing and a commit sit on the typing path; both are measured by the `NFR-PERF-002` bench.
- Startup verification is linear in the number of events; on very long histories it competes with the 2 s cold budget until the checkpoint-hash lever is pulled.

### Risks

- R-01: anchors drift on heavy edits. Property tests over random edit sequences and the revision-corpus metric at G1 are the gate; manual re-anchoring is the fallback.
- R-02: the view diverges from the log. `INV-02`, the fault-injection test, the `commit_failure` test and the replay property guard it.
- T-06: a bad write corrupts state. Chain verification, snapshot rebuild and ADR-0004's backups recover it. The chain detects accidents and truncation; it does not protect against someone who rewrites the whole chain, which is out of scope on a local-first machine (`INV-08`).

## Alternatives considered

- **CRDTs** ([PRD 21 §3](../prd/21-architecture-and-tech-stack.md#3-technology-decisions)). Rejected: one author edits at a time ([PRD 01 §3](../prd/01-vision-and-scope.md#3-non-goals-explicitly-out-of-scope), "not real-time collaborative"); a CRDT adds merge semantics nothing needs.
- **Snapshots only, no log.** Rejected: `INV-02`, `INV-05`, cross-session undo and the tool-call audit trail require the event sequence.
- **Recomputing segmentation on replay.** Rejected: any change to the segmenter would rewrite history and move every anchor.
- **Compacting old events into a snapshot.** Rejected: the append-only MUST and truncation detection; snapshots already give fast open.
- **BLAKE3 instead of SHA-256.** Viable and faster; not chosen because SHA-256 is already the project's checksum algorithm and the per-event cost is negligible. Revisit only with a measurement.
- **Storing snapshots as diffs.** Rejected: `FR-01-031` asks for content-addressed deduplication, which also makes `root_hash` comparison and diffing simple.
